Three questions decide the whole design, and one of them has a surprising answer.

Status: the GCP playground is live now. The shared AI engine described here launches in beta with V2 and opens to every workspace with V3.

Q1 · A project for every use case?

YES, one project per use case, never per person. It is the unit the register tracks, the budget funds, and the expiry clock retires.

Q2 · How do they reach the models?

Over the internal network only, one shared model server, one private address, no internet path in or out.

Q3 · An API key per person?

NO, not in v1, and not the way it sounds. The model server has no built-in keys or logins. Per-person keys are a service you would have to build. Attribution comes from projects instead, and that is what showback and the register actually need. Section 03 explains honestly what this does and doesn’t give you.

01 · Structure

One project per use case, not per person

The project is the container for everything that matters: access, budget, labels, expiry, and the register row. People are added into a use case’s project; they never get one of their own.

Workspace IDs encode the org path, prj-moenergy-iw-‹entity›-‹gd›-‹dept›-‹usecase›, e.g. it-dtgd-ad-ocr = ITDT · Digital Transformation GD · Applications Dept · OCR. The engine project keeps its own name. Full derivation rule in the operator guide.

✓ Do this

One project per use case, named from the org path: prj-moenergy-iw-‹entity›-‹gd›-‹dept›-‹usecase›.

Add people into it with IAM on that project only.

Three colleagues, one use case → one project, three members.

✕ Not this

A project per person, nothing to register, no owner, no expiry, cost meaningless.

One giant shared project, no isolation, no per-team cost, one expiry for everything.

Pre-created empty projects, governance debt with a clock running.

03 · Identity

The honest answer about API keys

You asked whether each person should get an API key so usage can be tracked per individual. Here is the truthful engineering answer, and what to do instead in v1.

What Ollama actually offers

The model server we run has no built-in authentication, no users, no logins, no API keys. Anyone who can reach port 11434 on the internal network can call any model, and the server does not know or record who they are.

So “give each person an API key” is not a setting to switch on. It is a service you would have to build and run in front of the model, a gateway that issues tokens, checks them on every call, and writes an identity into a log.

That is the right thing to build eventually, and the wrong thing to build first.

✓ v1, attribute by project (start here)

Network isolation is the control. Only sandbox workspaces can reach the endpoint at all.

Project = the unit of attribution. GPU cost, labels, budget and register row all roll up per use case.

People are known by project membership. IAM already records exactly who was added to which workspace, and audit logs record admin actions.

Zero extra components to build, secure, or hand over at day-90.

✕ Why not per-person keys in v1

Credential sprawl: keys emailed to individuals get shared, pasted into scripts, and outlive their owners, your own framework flags exactly this.

A service to run: a gateway needs uptime, rotation, and an owner, a second product before the first has proven value.

False precision: a key tells you which key called, not which human typed. Real identity needs SSO, which is the gateway path anyway.

It delays launch for a metric nobody has yet asked to see.

The decision: v1 attributes usage per use case, which is what showback, the register and the value scorecards all need. Per-person attribution arrives with the gateway (section 05), triggered by evidence, not by anticipation.

05 · The gateway

When per-person tracking earns its place

The gateway is a small service between workspaces and the model server. It is the right answer, later, and only when one of these triggers fires.

Trigger 1 · Scale

More than ~10 active workspaces, or the GPU regularly contended. You now need rate limits and fair queuing, which is a gateway job.

Trigger 2 · A real question

Someone with authority asks “who is using this most?” for a decision, not curiosity. Build it when the answer changes something.

Trigger 3 · Chargeback

Departments start paying for their own usage. Cost per prompt, per team, needs identity on the call path.

Build it as a backlog item, not a launch dependency. The architecture already anticipates it: because everything calls one address, inserting a gateway later changes one hostname in the welcome template, not a single workspace design. That is the whole reason the shared-engine pattern was chosen.
One project per use case. One private address. One shared GPU.

Isolation where it protects, sharing where it saves, and identity added the day it earns its cost, not before.
