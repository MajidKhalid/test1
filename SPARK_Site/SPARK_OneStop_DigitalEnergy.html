PAGE 1 · THE CASEwhy this, why now — and what you get
01 · The reality

AI is already inside the Ministry.
Governance and sovereignty are not.

Public AI tools are already part of daily work — unregistered, invisible, and crossing the border with every paste. That is the Ministry's live risk surface, and it grows on its own.

Invisible use

Unapproved tools in daily use with zero central visibility. The framework defines the KRI; today, nobody can report the number.

Data leaving the Kingdom

Every prompt pasted into a public tool is Ministry data crossing the border. Data classes offer no protection after the paste.

No gate in the way

Prohibited Tier-0 combinations — classified data into public tools — can occur today without a single gate, log or alarm in the path.

Cost enters last

AI gets promised to the business first; ITDT procures licences and hardware after the fact. Cost should enter the story first.

This does not need ten initiatives.
It needs one solution — taken seriously twice:
written, then run.

02 · The solution

One framework. Signed.
The Ministry's single answer to AI.

In July 2026 the Digital Enterprise Architecture GD delivered — and Cybersecurity co-signed — the AI Governance Framework: one register, risk tiers 0–5, NCA DCC data classes, lifecycle gates, KPIs and recertification. From that day there is one way AI enters the Ministry. This document is not context for a solution. It is the solution.

Each department keeps its mandate. The framework unifies them on paper; SPARK is the single place where that paper executes. No new rules — the signed ones, running.

State one — written · complete

Signed July 2026 by Digital EA and Cybersecurity. Register, lifecycle, tiers, data classes, KPIs — done, standards-aligned. Adopted, so far, by its authors.

State two — running · SPARK

Clauses executing by themselves: registration a side-effect, controls code, compliance measured live. Same framework, second state.

SPARK is not beside the framework.
SPARK is the framework — implemented.

That sentence is the whole strategy. Every page after this one is that sentence, unpacked.

03 · The product

SPARK as a service —
what you get, whoever you are

Strip the infrastructure away and SPARK is a simple promise: bring an idea, receive a governed AI workspace — with the Ministry's rules already running inside it. In service terms, five things arrive with every approval:

A governed workspace, in days

Your own project, your team added by name. Fast lane ≤ 1 day · guided ≤ 5 · full ≤ 15 — the framework's tiers, made fast.

Approved models, on tap

Pre-approved, locally-hosted models served from Ministry GPU — call an internal endpoint and build. No keys to beg for, no vendor contract.

Your data stays yours

Per-project isolation: sharing the model never shares the data. Nothing you bring leaves the Ministry boundary — structurally.

Spend, visible and guarded

A budget is born with the workspace; you are emailed at every threshold. Prototype guardrails at roughly the $100 scale — nothing runs away quietly.

A route to production

Demo with evidence, then graduate through Emerging Technologies' scale path — or retire cleanly with lessons kept. No orphans.

And one thing you never do

Paperwork. Registration, logging, cost labels and recertification dates happen as a side-effect of using SPARK — the framework works for you.

Three customer groups — one pipeline serves them all

Innovators in the KSA energy ecosystem

An idea with energy in it deserves better than a slide. Through a Ministry sponsor, SPARK is where an energy AI concept meets real compute and real governance — proved against real problems, without procurement, without data risk, with a graduation path if it works.

Ministry teams that build

From shadow AI to a sanctioned lane. The fastest compliant route from idea to working prototype in the Ministry: apply in minutes, build in days, models and register handled for you. The safe path is finally also the easy one.

Every employee — through published use cases

You never have to build to benefit. Use cases that prove value graduate, and graduation ends in publication: validated, governed tools any employee in the ecosystem can adopt — without ever opening a workspace. Innovators build once; the framework validates; publication scales it to everyone.

And the mandate owners are served, not sidelined

Beyond its customers, SPARK serves the governors — every mandate owner consumes assurance from the same running system.

Cost before commitment

Every AI-GD proposal is priced in SPARK before procurement. One avoided unfunded commitment can exceed the entire annual run cost.

The spend guardrails — as built

Cost data lags by hours — so the forecasted threshold is the early warning, and the killswitch is the backstop. The moving dot is the point: alerts fire while spend is still climbing, not after it lands.

Budget A — every workspace

Alerts, not caps. One budget per project, all services, monthly: thresholds at 50 / 85 / 100% actual + 100% forecasted, read-only for project users, requester emailed directly, every event published to Pub/Sub spark-budget-alerts. Prototype workspaces run at roughly the $100 scale.

Budget B — only where managed AI APIs run

A real cap, honestly scoped. Spend-cap enforcement on Vertex AI / Gemini API where a workspace uses them. GCP's cap covers Cloud Run, Vertex AI, Cloud Run Functions and Gemini API — not Compute Engine, so it cannot protect the GPU VM.

The killswitch — the backstop

One shared Pub/Sub topic, one Cloud Run function in the admin project: it stops VMs — reversible — and never disables billing. Paired with the idle GPU schedule (19:00–07:00 stop, Sun–Thu), which prevents most overnight burn.

Stated plainly

Budgets alert, they do not cap — enforcement is the killswitch. Cost data lags several hours, so the 100%-forecasted threshold is the early warning that fires while spend is still climbing, and the killswitch is the backstop behind it. The idle GPU schedule prevents most overnight burn. And because GCP's spend cap does not reach Compute Engine, GPU spend is controlled by exactly those three — alerts, schedule, killswitch — not by a cap.

Value figures are an illustrative planning model; signed scorecards replace the model as evidence accumulates. The guardrail design above is as built on the operations side — full procedure in the operator guide.
