THE THREE RULES — everything else is detail

1 · Never act above the Sandbox folder. Your keys open one room, on purpose. That scoping is your protection.

3 · When unsure about networks or policies — ask Cloud Computing. Escalating correctly is what makes an admin trusted, not knowing everything.

Install the model server — one command TYPE

On the VM row, click SSH (a terminal opens in your browser — that's you, inside the machine). Then:

curl -fsSL https://ollama.com/install.sh | sh

Ollama is the serving software — it downloads, runs and exposes the models. It auto-detects the GPU.

3

Let it listen on the private network, then pull the first models TYPE

sudo sh -c 'mkdir -p /etc/systemd/system/ollama.service.d && printf "[Service]\nEnvironment=OLLAMA_HOST=0.0.0.0\n" > /etc/systemd/system/ollama.service.d/override.conf' sudo systemctl daemon-reload && sudo systemctl restart ollama
ollama pull llama3.1:8b ollama pull qwen2.5:7b ollama pull mistral:7b

WAIT a few GB each. Then the moment of truth:

ollama run llama3.1:8b "Say hello from SPARK, in Arabic and English."

If it answers — the Ministry just ran its first fully local AI model. Screenshot it. (ALLaM joins the catalog later via a model-file import — a Phase-6 refinement, not a day-1 need.)

4

Open the endpoint to sandbox workspaces only TYPE

Back in Cloud Shell (not the VM). Replace NETWORK and the source range with Cloud Computing's answers:

gcloud compute firewall-rules create spark-allow-internal-ollama --project=prj-moenergy-spark-000-eng --network=NETWORK --allow=tcp:11434 --source-ranges=10.0.0.0/8 --target-tags=spark-model-server
5

Make the GPU sleep — the single biggest cost control CLICK

Compute Engine › Instance schedules › CREATE SCHEDULE

Stop 19:00 · Start 07:00 · Sun–Thu, region me-central2 → attach spark-model-server. A stopped GPU VM costs ~disk only. This one schedule is worth more than every other cost control combined.

✅
Phase-2 definition of done: model answers over SSH · firewall rule exists · sleep schedule attached · you noted the VM's internal IP (VM list → Internal IP column) — workspaces will call http://INTERNAL_IP:11434.

How a workspace actually calls the model API TYPE

From any approved workspace project (never from outside), the whole integration is one HTTP call. Test with curl:

curl http://10.20.0.5:11434/api/generate -d '{"model":"llama3.1:8b","prompt":"Say hello from inside the Ministry boundary","stream":false}'

Or from a Python notebook:

import requests r = requests.post("http://10.20.0.5:11434/api/generate", json={"model":"qwen2.5:7b","prompt":"Summarize this document: ...","stream":False}) print(r.json()["response"])

That address only exists inside the Ministry VPC — the same code pasted anywhere on the internet resolves to nothing. Which is the whole point.

4

Budget B — the real cap, only where managed AI APIs run CLICK

For workspaces that use Vertex AI or the Gemini API, add spend-cap enforcement on those services. Be honest about its reach: GCP's spend cap covers Cloud Run, Vertex AI, Cloud Run Functions and the Gemini API — not Compute Engine. It can stop a runaway managed-API bill; it cannot protect the GPU VM. Most SPARK workspaces call the shared engine over the internal network and never touch a managed AI API — for them, Budget A + the killswitch is the whole story and Budget B simply doesn't apply.

5

The killswitch — one function, one job TYPE

One shared Pub/Sub topic (spark-budget-alerts) receives every budget event. One Cloud Run function in the admin project subscribes to it. When a 100%-forecast or 100%-actual event arrives, it stops the workspace's VMs — a reversible action — and emails you and the owner. It never disables billing: billing disable deletes resources and destroys work; stopping VMs pauses spend and preserves everything. Restart is one click after the conversation.

The guardrail truths — say them plainly in every review

1 · Budgets alert, they do not cap. Enforcement is the killswitch, not the budget. 2 · Cost data lags several hours — so the 100%-forecasted threshold is the early warning that fires while spend is still climbing, and the killswitch is the backstop behind it. 3 · The idle GPU schedule (19:00 stop / 07:00 start, Sun–Thu) prevents most overnight burn — it is the single biggest cost control in the whole design. 4 · GCP's spend cap does not reach Compute Engine. It covers Cloud Run, Vertex AI, Cloud Run Functions and the Gemini API only — so GPU-VM spend is controlled by Budget A alerts, the idle schedule and the killswitch, never by a cap.

Phase 4 · The workspace recipe

The 20-minute recipe you'll repeat forever

This is the core admin skill. Every approved use case gets the same eight moves — same order, every time. Print this section.

Naming a workspace — the derivation rule (no list to look up)

Every workspace ID is derived, not invented — it encodes the requester's place in the org chart, so anyone can name a new workspace unaided:

prj-moenergy-iw-‹entity›-‹gd›-‹dept›-‹usecase›

Fixed prefix prj-moenergy- — org policy enforces it (verified by test) · iw = Isolated Workloads, the folder family · ‹entity› = the requester's entity code (e.g. it = ITDT) · ‹gd› = their general department (e.g. dtgd = Digital Transformation GD) · ‹dept› = their department (e.g. ad = Applications Dept) · ‹usecase› = a short tag for the case (≤ 4 chars: ocr, rag, fcst, ne).

Worked example: prj-moenergy-iw-it-dtgd-ad-ne = ITDT · Digital Transformation GD · Applications Dept · Notification Center. Hard limit: project IDs cap at 30 characters — keep segment codes to 2–4 chars and the whole ID fits. The one exception: the shared engine keeps its fixed name prj-moenergy-spark-000-eng — it is platform, not a requester workspace. Take dept codes from the official org structure circular; never make one up.

The register · One inventory

The AI Register — an inventory that updates itself

The Register (framework Clause 22) is the official inventory of every AI use in the Ministry — vendor SaaS, department tools, AI-GD solutions, and SPARK alike. EA owns its definition; you operate it day to day. The trick that makes it sustainable: the two busiest feeders write their own rows.

Watch it update itself — press the events

This is the exact mechanic, miniaturized. Two feeders are people acting in their own interest (getting a workspace, getting protected); their action is the register entry. You screen and route — you never chase.

Press an event above — the register reacts the way it will in production.

Your register rhythm (runs as R3)

Weekly 30 min: new rows entered, statuses touched, zero TBD owners. Monthly 2 h: ingest the feeds, reconcile, refresh the Command Centre, ship the digest. Quarterly ½ day: recert sweep — every row past Next Review gets an owner attestation or a retirement.

Why this stays honest

SPARK rows can't be forgotten — creation writes them. Non-SPARK rows have a self-service door (the intake page) plus two safety nets that don't rely on goodwill: procurement's PO scan and Cyber's shadow-AI count. Coverage rises structurally, not by campaign.

Phase 5 · Operate

Running SPARK is not a job of hours — it's a job of rhythm. Three loops, strictly time-boxed:

Daily · 10 min

Open the Looker dashboard with your coffee. Two questions: any workspace trending past its budget line? Is the GPU asleep when it should be? Anomaly → message the owner, same day.

Weekly · ~2 hrs

Tuesday office hours (1h, standing invite). Then: cost review, register touch-up, one welcome/decommission batch, one line to Nasser: "N active, X spend, no incidents."

Monthly · ~half day

When things break

Six failures you'll actually meet

"Quota exceeded" creating the GPU VM

Phase-0 check missed or zone-specific. Try another me-central2 zone; else request the quota increase (Phase 0, step 3) and run the contingency. Not a crisis — a queue.

VM created but model is slow / CPU-only

SSH in → nvidia-smi. No GPU listed → the instance was created without the accelerator: delete VM, recreate with GPUs = 1 (disk survives if you kept it).

Workspace can't reach the endpoint

Three checks in order: VM running (schedule!) · firewall rule exists with tag spark-model-server · workspace is on the template subnet. 90% it's the first one.

Budget email at 100%

Dashboard → which label spiked → message the owner same hour → if runaway, stop their VMs (their project → Compute → Stop). Reversible, data-safe. Never touch billing links — that's Cloud Ops, last resort.

"Permission denied" on something you expected

Check which project the console picker shows first — 80% of the time you're in the wrong project. If genuinely missing on the folder: quote the exact role name to Cloud Computing.

A user pastes Secret data into a fast-lane workspace

Not a tech fix. Stop the workspace, note it in the register, apply the framework's incident path with Cybersecurity, re-lane the use case. Handling one of these correctly builds more trust than a year of uptime.
